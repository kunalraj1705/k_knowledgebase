# GitHub Actions Knowledge Base

## 1. Overview

GitHub Actions is GitHub's automation and CI/CD platform.

It allows software-development workflows to be triggered automatically by repository events such as:

- Pushes
- Pull requests
- Other supported GitHub events

A typical software delivery flow is:

```text
Source Code
    ↓
GitHub Repository
    ↓
GitHub Actions
    ↓
Build
    ↓
Test
    ↓
Package
    ↓
Container Image
    ↓
Container Registry
    ↓
Deployment
```

GitHub Actions can therefore automate both **Continuous Integration (CI)** and **Continuous Delivery/Deployment (CD)**.

---

# 2. CI/CD Fundamentals

## 2.1 Continuous Integration

Continuous Integration means frequently integrating code changes into a shared repository and automatically validating those changes.

A CI pipeline commonly performs:

```text
Code Change
    ↓
Build
    ↓
Test
    ↓
Validation
```

The objective is to detect problems as early as possible.

### Key characteristics

- Automated builds
- Automated tests
- Frequent integration
- Fast feedback
- Consistent validation environment

---

## 2.2 Continuous Delivery

Continuous Delivery extends CI by keeping the application in a deployable state.

```text
Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Deployable Artifact
```

Deployment can then be performed when desired.

---

## 2.3 Continuous Deployment

Continuous Deployment goes one step further:

```text
Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Deploy Automatically
```

A successful pipeline can automatically release the validated artifact to an environment.

# 3. GitHub Actions Core Concepts

A GitHub Actions automation system is built from several core concepts:

```text
Workflow
   │
   ├── Event
   │
   └── Jobs
         │
         ├── Runner
         │
         └── Steps
                │
                └── Actions / Commands
```

The important terms are:

- Workflow
- Event
- Job
- Runner
- Step
- Action
- Command
- Context
- Variables
- Secrets
- Permissions

---

# 4. Workflow

A **workflow** is an automated process defined using YAML.

Workflow files are stored under:

```text
.github/workflows/
```

A workflow describes:

- When automation should run
- What jobs should run
- Which runner should execute the jobs
- Which steps should be performed
- What permissions and configuration are required

Example structure:

```yaml
name: CI

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v5

      - name: Build
        run: ./mvnw clean verify
```

The YAML file is therefore the declarative definition of the automation pipeline.

---

# 5. Events

The `on` section defines **when a workflow is triggered**.

Examples covered:

```yaml
on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main
```

This means the workflow can run for:

```text
Push to main
      ↓
Workflow triggered

Pull request targeting main
      ↓
Workflow triggered
```

Events are the entry points of a GitHub Actions workflow.

---

# 6. Push Events

A push event occurs when commits are pushed to a repository.

For example:

```yaml
on:
  push:
    branches:
      - main
```

This limits the trigger to pushes affecting the `main` branch.

A push to `main` can therefore initiate:

```text
git push
    ↓
GitHub receives commit
    ↓
Workflow starts
```

---

# 7. Pull Request Events

A pull request event allows code changes to be validated before they are merged.

Example:

```yaml
on:
  pull_request:
    branches:
      - main
```

Typical flow:

```text
Feature Branch
      ↓
Pull Request
      ↓
GitHub Actions
      ↓
Build + Test
      ↓
Validation
      ↓
Merge
```

This allows CI to act as a quality gate.

---

# 8. Jobs

A workflow contains one or more **jobs**.

Example:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
```

A job is a logical unit of work.

Conceptually:

```text
Workflow
   │
   ├── build job
   ├── test job
   └── deploy job
```

Jobs can be organized so that different responsibilities are separated.

A job executes its steps on a runner.

---

# 9. Runners

A **runner** is the machine/environment where a GitHub Actions job executes.

Example:

```yaml
runs-on: ubuntu-latest
```

This requests a GitHub-hosted Ubuntu runner.

Conceptually:

```text
GitHub Actions
      ↓
Job
      ↓
Runner
      ↓
Commands / Actions execute
```

The runner provides the environment needed by the workflow.

---

# 10. Steps

A job contains ordered steps.

Example:

```yaml
steps:
  - name: Checkout
    uses: actions/checkout@v5

  - name: Build
    run: ./mvnw clean verify
```

Steps execute sequentially within a job.

A step can:

1. Use a reusable GitHub Action.
2. Execute a shell command.

---

# 11. `uses` vs `run`

Two important ways to define a step are:

### `uses`

Uses an existing reusable action:

```yaml
- name: Checkout source
  uses: actions/checkout@v5
```

### `run`

Executes a command:

```yaml
- name: Build and test
  run: ./mvnw clean verify
```

Conceptually:

```text
uses → reusable action

run  → shell command
```

---

# 12. GitHub Actions

An **Action** is a reusable unit of automation.

Examples covered:

```text
actions/checkout
actions/setup-java
docker/setup-buildx-action
docker/login-action
docker/build-push-action
```

Actions encapsulate commonly required automation so workflows do not need to implement everything manually.

---

# 13. Repository Checkout

Before a runner can build application source code, the repository contents need to be available in the runner workspace.

The standard action is:

```yaml
uses: actions/checkout@v5
```

It retrieves repository content into the workflow environment.

Conceptually:

```text
GitHub Repository
       ↓
actions/checkout
       ↓
Runner Workspace
       ↓
Build / Test
```

---

# 14. Multiple Repository Checkout

A workflow can check out more than one repository.

A checkout can specify a destination:

```yaml
with:
  path: k_enterprise
```

Another repository can be checked out into another path:

```yaml
with:
  repository: owner/repository
  path: k_enterprise_infra
```

This produces a workspace such as:

```text
Runner
│
├── k_enterprise
│
└── k_enterprise_infra
```

This is useful when a delivery process depends on separate application and infrastructure repositories.

---

# 15. Java Setup

GitHub Actions can provision the required Java runtime using:

```yaml
uses: actions/setup-java@v5
```

Example:

```yaml
with:
  java-version: '25'
  distribution: 'temurin'
  cache: maven
```

Important concepts:

- Java version
- Distribution
- Dependency caching

The Java setup action establishes the Java environment required by subsequent build steps.

---

# 16. Dependency Caching

The Java setup action can enable Maven dependency caching:

```yaml
cache: maven
```

Conceptually:

```text
First build
    ↓
Download Maven dependencies
    ↓
Cache dependencies

Later build
    ↓
Reuse cached dependencies
    ↓
Faster build
```

Caching improves pipeline efficiency without changing application behavior.

---

# 17. Maven Build in CI

A workflow can execute the project's Maven wrapper directly:

```yaml
run: ./mvnw clean verify
```

This allows CI to perform the same build and verification lifecycle used by the project.

Conceptually:

```text
Checkout
   ↓
Java setup
   ↓
Maven
   ↓
Compile
   ↓
Test
   ↓
Verify
```

Using the Maven Wrapper helps keep the Maven version controlled by the project rather than depending on a globally installed Maven version.

---

# 18. Testcontainers in CI

Integration tests can require external infrastructure such as PostgreSQL.

Testcontainers allows tests to create disposable containers during test execution.

Conceptually:

```text
GitHub Actions Runner
       ↓
Testcontainers
       ↓
PostgreSQL Container
       ↓
Integration Tests
```

This provides a self-contained test environment.

The important CI principle is:

> CI should not depend on a developer's local database or other local infrastructure.

---

# 19. Workflow Permissions

GitHub Actions workflows can explicitly declare permissions.

Example:

```yaml
permissions:
  contents: read
  packages: write
```

Permissions follow the principle of granting the workflow only the access it requires.

In this case:

```text
contents: read
    ↓
Read repository content

packages: write
    ↓
Publish packages / container images
```

Explicit permissions make the security model easier to understand and control.

---

# 20. `GITHUB_TOKEN`

GitHub provides a workflow token that can be accessed as:

```text
secrets.GITHUB_TOKEN
```

It can be used by workflows to authenticate against supported GitHub services.

For package publishing, the token can be used when the workflow has the required package permission.

Conceptually:

```text
GitHub Actions
      ↓
GITHUB_TOKEN
      ↓
GitHub service
```

This avoids unnecessarily creating a separate long-lived credential for supported GitHub operations.

---

# 21. Secrets

Secrets are sensitive values that should not be hardcoded into workflow files.

Examples of values that should generally be treated as secrets:

- Passwords
- Private keys
- Access tokens
- Deployment credentials

Conceptually:

```text
Secret Store
     ↓
Workflow
     ↓
Runtime use
```

The secret itself should not be committed into source control.

---

# 22. GitHub Actions and Docker

GitHub Actions can build Docker images using Docker-specific actions.

The Docker workflow can be:

```text
Application source
       ↓
Maven build + tests
       ↓
Docker build
       ↓
Container image
```

Buildx can be initialized with:

```yaml
uses: docker/setup-buildx-action@v3
```

The Docker image can then be built using:

```yaml
uses: docker/build-push-action@v6
```

---

# 23. Docker Build Context in CI

A Docker build has:

- Dockerfile
- Build context

These are separate concepts.

Example:

```yaml
context: k_enterprise
file: k_enterprise_infra/docker/Dockerfile
```

This means:

```text
Dockerfile
    → infrastructure repository

Build context
    → application repository
```

The Dockerfile can therefore be maintained separately from the application source while still building the application correctly.

---

# 24. Build Once, Publish the Artifact

A CI pipeline can produce a container image as a delivery artifact.

Conceptually:

```text
Source Commit
      ↓
Build + Test
      ↓
Docker Image
      ↓
Container Registry
```

The image can then be consumed by deployment environments.

This creates a separation between:

```text
Build
```

and:

```text
Deploy
```

The same built artifact can be promoted between environments rather than rebuilding the application independently for every environment.

---

# 25. GitHub Container Registry (GHCR)

GitHub Container Registry is a container registry integrated with GitHub.

Its registry hostname is:

```text
ghcr.io
```

A fully qualified container image has the general form:

```text
ghcr.io/<owner>/<image>:<tag>
```

Example:

```text
ghcr.io/kunalraj1705/k_enterprise:latest
```

The registry acts as the shared location between CI and deployment environments.

---

# 26. Docker Login to GHCR

A workflow can authenticate to GHCR using:

```yaml
- name: Log in to GHCR
  uses: docker/login-action@v3
```

Conceptually:

```text
GitHub Actions
      ↓
Authenticate
      ↓
GHCR
      ↓
Push image
```

Authentication should use appropriate credentials/tokens rather than embedding credentials directly in the workflow.

---

# 27. Docker Image Publishing

The Docker build/publish action can perform both building and publishing.

Conceptually:

```text
Build
  ↓
Tag
  ↓
Push
```

The `push` behavior can be controlled.

For example:

```yaml
push: ${{ github.event_name == 'push' }}
```

This creates different behavior for pull requests and normal pushes.

---

# 28. Pull Request vs Main Branch Publishing

A useful CI policy is:

```text
Pull Request
    ↓
Build
    ↓
Test
    ↓
Docker build
    ↓
Do NOT publish

Push to main
    ↓
Build
    ↓
Test
    ↓
Docker build
    ↓
Publish image
```

This prevents every pull request from publishing a container image while still validating that the Docker build works.

---

# 29. Docker Image Tags

A Docker image can have multiple tags.

Two useful tag categories are:

```text
latest
```

and:

```text
commit SHA
```

Example:

```text
ghcr.io/kunalraj1705/k_enterprise:latest

ghcr.io/kunalraj1705/k_enterprise:<commit-sha>
```

---

# 30. `latest` Tag

`latest` is a moving tag.

For example:

```text
Commit A
   ↓
latest → A

Commit B
   ↓
latest → B
```

The name `latest` does not identify a permanent version.

It is convenient but should not be treated as an immutable release identifier.

---

# 31. Commit SHA Tag

A commit SHA tag associates an image with a particular source revision.

Conceptually:

```text
Git commit
    ↓
github.sha
    ↓
Docker image tag
```

Example:

```text
ghcr.io/kunalraj1705/k_enterprise:abc123...
```

This provides traceability between:

```text
Source revision
       ↕
Container image
```

It is especially useful for controlled deployments and rollback.

---

# 32. Immutable Deployment Concept

For controlled environments, a deployment can use a specific image tag rather than `latest`.

Example:

```env
IMAGE_TAG=<commit-sha>
```

Compose then resolves:

```yaml
image: ghcr.io/kunalraj1705/k_enterprise:${IMAGE_TAG}
```

Conceptually:

```text
IMAGE_TAG
    ↓
Commit SHA
    ↓
Exact container image
    ↓
Deployment
```

This makes it possible to determine which source revision is running.

---

# 33. Environment Variables in Compose + CI/CD

Docker Compose can use variable substitution:

```yaml
image: ghcr.io/kunalraj1705/k_enterprise:${IMAGE_TAG}
```

A `.env` file can provide the value during local development:

```env
IMAGE_TAG=latest
```

Compose resolves:

```text
${IMAGE_TAG}
      ↓
latest
```

and obtains:

```text
ghcr.io/kunalraj1705/k_enterprise:latest
```

The same Compose definition can therefore work with different image tags without modifying the YAML file.

---

# 34. Registry as the CI/CD Bridge

A container registry decouples image creation from image consumption.

```text
                CI
                 │
                 │ push
                 ▼
               GHCR
                 │
                 │ pull
                 ▼
            Deployment
```

CI does not need to transfer the image directly to the deployment machine.

The registry provides the shared artifact location.

---

# 35. CI/CD Separation

A mature pipeline separates responsibilities:

```text
CI
│
├── Checkout
├── Build
├── Test
├── Package
└── Publish Artifact
```

Then:

```text
CD
│
├── Select Artifact
├── Deploy
├── Verify
└── Roll Back if required
```

This separation improves traceability and makes deployment automation easier to control.

# 37. Important Engineering Principles

### Principle 1 — CI must be reproducible

Do not depend on developer-local infrastructure.

### Principle 2 — Validate before publishing

Build and test before publishing a delivery artifact.

### Principle 3 — Keep credentials outside source code

Use appropriate secret and token mechanisms.

### Principle 4 — Minimize workflow permissions

Grant only the permissions required by the workflow.

### Principle 5 — Separate application and infrastructure concerns

Application source and infrastructure configuration can be maintained independently.

### Principle 6 — Build artifacts should be traceable

A container image should be associated with the source revision that produced it.

### Principle 7 — Avoid relying exclusively on `latest` for controlled environments

Use immutable or uniquely identifiable tags for controlled deployments.

### Principle 8 — Separate CI from CD

CI produces and validates artifacts; CD deploys validated artifacts.
