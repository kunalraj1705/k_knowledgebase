# GitHub Actions — UAT Deployment Concepts

**Session:** GitHub Actions CD / UAT  
**Date:** 7 September 2026  
**Status:** Concepts learned today

## 1. CI vs CD

CI validates source changes:

```text
Code → Build → Test → Package
```

CD moves a validated artifact into an environment:

```text
Validated Artifact → Environment → Deploy → Verify
```

A strong pipeline follows:

```text
Build once
Deploy the same artifact
```

## 2. Artifact Promotion

A Docker image is a deployable artifact.

```text
Source
  ↓
CI
  ↓
Docker Image
  ↓
Container Registry
  ↓
UAT
```

UAT should consume the artifact produced by CI instead of rebuilding it.

## 3. Container Registry as the CI/CD Bridge

The registry separates build infrastructure from deployment infrastructure.

```text
GitHub Actions
      ↓
Container Registry
      ↓
UAT
```

CI publishes the image.

Deployment infrastructure pulls the image.

## 4. Image Tags and Reproducibility

`latest` is convenient but mutable.

A commit SHA identifies a specific source revision and therefore provides a much stronger deployment reference.

```text
latest → mutable

SHA → specific build
```

For controlled deployments:

```text
k_enterprise:<commit-sha>
```

supports reproducibility and rollback.

## 5. GitHub Environments

A GitHub Environment represents an environment-specific deployment boundary.

Examples:

```text
Development
UAT
Production
```

A workflow job can target an environment:

```yaml
environment: UAT
```

An environment can provide:

- secrets
- variables
- protection rules
- deployment controls

## 6. Environment Separation

Generic workflow logic should be separated from environment-specific configuration.

```text
Pipeline
   ↓
Environment boundary
   ├── configuration
   ├── secrets
   └── protection
```

This makes the same deployment logic reusable across environments.

## 7. Variables vs Secrets

Variables are appropriate for non-sensitive configuration.

Secrets are for sensitive values such as:

- passwords
- credentials
- tokens
- private keys

Sensitive values should not be hard-coded into workflows.

## 8. GitHub-Hosted vs Self-Hosted Runners

GitHub-hosted runner:

```text
GitHub Actions → GitHub-managed machine
```

Self-hosted runner:

```text
GitHub Actions → Organization-controlled machine
```

Self-hosted runners are useful when deployment must happen inside a private network or on infrastructure that GitHub-hosted runners cannot directly reach.

## 9. Self-Hosted Runner Labels

Runners can have labels describing their capabilities or environment.

Example:

```text
self-hosted
linux
x64
uat
```

A workflow can target matching labels:

```yaml
runs-on: [self-hosted, linux, x64, uat]
```

This allows deployment jobs to be directed to the correct infrastructure.

## 10. Self-Hosted Runner Security

A self-hosted runner executes workflow code on infrastructure controlled by the organization.

Therefore:

```text
Workflow
   ↓
Self-hosted runner
   ↓
Host access
```

is a significant security boundary.

Important principles:

- restrict workflow modification
- minimize runner privileges
- isolate production runners
- use environment protection
- avoid unnecessary host credentials
- treat deployment workflows as privileged code

## 11. Docker Compose Deployment

Compose defines and orchestrates a group of services.

Conceptually:

```text
Compose
 ├── Application
 ├── Database
 ├── Network
 └── Volumes
```

Deployment can involve:

```text
Pull image
   ↓
Create/update containers
   ↓
Attach network
   ↓
Mount volumes
   ↓
Start services
```

## 12. `depends_on` vs Health

Startup ordering and service health are different concepts.

```text
Database
   ↓
starting
   ↓
running
   ↓
healthy
   ↓
application starts
```

Important:

```text
running ≠ healthy
```

A healthcheck provides a condition that can be used for dependency startup ordering.

## 13. Startup Ordering vs Runtime Recovery

`depends_on` controls startup orchestration.

It does not provide complete runtime failure recovery.

```text
Startup
   ↓
depends_on
   ↓
service starts
```

Runtime recovery is a separate concern:

```text
Application running
        ↓
Dependency temporarily unavailable
        ↓
Client/application recovery
```

## 14. Compose Environment Substitution

Compose files can use:

```text
${VARIABLE}
```

This separates deployment definition from environment-specific values.

Conceptually:

```text
compose.yaml
      +
environment values
      ↓
resolved deployment configuration
```

## 15. Docker Snap Confinement

Snap applications can run inside a confinement boundary.

Therefore:

```text
Linux user access
```

and:

```text
Snap application access
```

are not equivalent.

A shell user may be able to read a file while a confined Snap application cannot.

## 16. Snap Interfaces

Snap interfaces control access to certain host resources.

Examples include:

```text
home
network
removable-media
```

Connecting an interface does not provide unrestricted filesystem access.

The available interfaces determine what resources the confined application can access.

## 17. Diagnosing Sandboxed Filesystem Problems

When:

```text
file exists
+
shell can read it
+
application cannot open it
```

investigate:

- Unix permissions
- AppArmor
- Snap confinement
- container isolation
- filesystem namespace restrictions

The key diagnostic question is:

```text
Can the actual application/tool access the resource?
```

not only:

```text
Can the shell user access the resource?
```

## 18. Tool Installation Method Matters

The same command can behave differently depending on how its executable was installed.

For CI/CD troubleshooting, consider:

```text
Workflow
+
Runner
+
Operating system
+
Tool installation
+
Sandbox/confinement
```

This is especially important when tools are installed through package systems that enforce isolation.

## 19. Deployment Boundary Model

A deployment pipeline crosses multiple boundaries:

```text
Source Control
      ↓
CI Runner
      ↓
Artifact Registry
      ↓
Deployment Runner
      ↓
Container Runtime
      ↓
Application Environment
```

Each boundary may introduce:

- authentication
- authorization
- network restrictions
- filesystem restrictions
- configuration
- security controls

## 20. Senior Troubleshooting Pattern

Use this sequence:

```text
1. Does the resource exist?
2. Can the OS user access it?
3. Can the actual tool access it?
4. Is the tool sandboxed?
5. What interfaces/permissions does it have?
6. Is the failure environment-specific?
```

The goal is to identify the failing boundary before modifying infrastructure.

## 21. Key Takeaways

- CI validates changes; CD deploys validated artifacts.
- Registries bridge CI and deployment environments.
- SHA tags improve reproducibility.
- GitHub Environments separate deployment configuration and protection.
- Self-hosted runners are useful for private environments.
- Runner labels allow targeted deployment.
- Self-hosted runners are security-sensitive infrastructure.
- `depends_on` is primarily startup orchestration.
- `running` and `healthy` are different states.
- Compose supports environment-variable substitution.
- Tool installation method can affect behavior.
- Snap confinement is separate from Unix permissions.
- A user having filesystem access does not guarantee a confined application has the same access.
- Good troubleshooting identifies the failing boundary before changing infrastructure.
